# @delthin/dsh-feishu-notify

简体中文 | [English](./README.en.md) | [更新日志](./CHANGELOG.md)

从 DeepSeek Harness（DSH）宿主向飞书自建应用的指定接收方（私聊或群聊）发送单向提醒通知。关闭浏览器不影响自动提醒发送；插件仅用于单向发送提醒，不接收飞书消息，也不建立长连接。

- **包名**：`@delthin/dsh-feishu-notify`
- **当前版本**：`1.1.0`
- **仓库位置**：源码仓库 `Delthin/dsh-plugins` 的 `packages/feishu-notify` 子目录
- **运行环境**：Node.js >= 22，DSH >= 0.2.1-rc.5（当前验证基准 `0.2.2-rc.1`）
- **许可证**：`PolyForm-Noncommercial-1.0.0`（见仓库根目录 [`LICENSE`](../../LICENSE)）

## 功能概览

### 1. 长任务收尾通知（`notify_user`）

插件向模型注入独立系统提示词，沿用“提示词约束 + 通知工具”的方式，由执行任务的模型主动生成摘要并调用 `notify_user`，宿主不再逐回合补发，也不额外调用独立的摘要模型：

- **触发条件**：用户请求的整体工作持续至少 3 分钟时，在完成或收尾时调用 `notify_user` 一次。
- **排除范围**：子任务、中间进度、简短问答和内部异常不发送通知。
- **参数与格式**：`message` 填写简短工作摘要，`title` 可选。手机端正文按需包含 `✅ 完成事项`、`❌ 仍未完成`、`👉 待用户处理`，无对应事项则省略；每项最多 32 个 Unicode 字符。正文不包含 profile、会话 ID 或调试前缀。
- **发送控制与回执**：工具仅向已保存的接收方发送，遵守总开关（`enabled`）、免打扰时段（`quietHours`）和子代理过滤，返回实际的 `success`、`skipped` 或 `failed` 回执。
- **去重与幂等边界**：整体任务的时间与边界由模型按上下文判断，宿主不会把“当前回合已满 3 分钟”直接判定为整项任务完成。代码层会拦截同一回合（turn）内的并发调用或成功后的重复调用，并将成功回执写入会话投影（重载后仍可识别），失败或跳过不占用成功名额。但跨回合（cross-turn）不重复通知依赖模型遵守提示词约束，系统没有跨回合的稳定任务 ID 自动幂等机制。

### 2. 宿主事件自动提醒

宿主仅对需要用户介入的特定事件触发自动提醒，忽略子代理事件：

- **已接入事件**：审批请求、向用户提问、计划确认通知。
- **不触发事件**：普通回复结束（turn-end）、会话结束（session-end）、运行失败或中断均不自动发送通知，也不会因此调用摘要模型或写入发送记录。
- **事件去重**：同一事件在 60 秒内仅提交一次发送，网络重试复用同一个请求 UUID。

### 3. 状态查询、配置与测试工具（`feishu_notify`）

`feishu_notify` 工具供模型或宿主执行辅助操作：

- **状态查询（`status`）**：读取当前启用状态、配置摘要与最近发送结果，不发送飞书消息。
- **非密钥配置（`configure`）**：更新除密钥外的配置字段（模型无法通过任何工具读取或修改 `App Secret`）。
- **固定测试消息**：发送真实固定测试文案以验证飞书通道连通性。测试消息使用已保存的配置，忽略总开关（`enabled`）和免打扰时段（`quietHours`）。

### 4. 通信与可靠性

- HTTP 请求使用 Node.js 内置 `fetch`，单次请求（含响应体读取）超时时间为 5 秒。
- 网络错误与 HTTP 5xx 响应最多重试 3 次；飞书接口业务错误（`code !== 0`）直接报错返回，不视为成功。
- `tenant_access_token` 按飞书接口返回的有效期缓存并提前刷新；修改应用凭据后自动清空缓存。

## 安装与升级

### 安装与导入

通过 npm 安装（或按宿主支持的本地包/压缩包导入方式接入 DSH）：

```sh
npm install @delthin/dsh-feishu-notify
```

按当前 DSH 宿主的插件导入或 bundle 挂载方式启用插件。插件复用宿主已有的 `webServer` 服务注册路由，不创建额外监听端口。安装或更新宿主模块后，请刷新设置页面并按宿主提示重启 DSH。

### 源码检查与打包

在仓库根目录执行依赖安装、静态检查、单元测试与工作区打包：

```sh
npm ci --ignore-scripts
npm run check
npm pack --workspace @delthin/dsh-feishu-notify
```

在子包目录内也可直接执行语法与单元测试验证：

```sh
node --check index.js
node --check client.js
node --test core.test.js summary.test.js
```

### 从非作用域旧包升级

包名已迁移为 `@delthin/dsh-feishu-notify`，但内部服务标识、设置页面 ID 及 profile 配置文件名均保持 `feishu-notify` 不变。升级时只需替换包名与资源路径，切勿在同一环境中同时启用旧版与新版实例。升级前请先备份当前 profile 下已有的 `feishu-notify.json`。

## 配置说明

在 DSH Web 界面进入「设置 → 飞书提醒」，填写配置并保存后启用。配置保存在当前运行 profile 的 `feishu-notify.json` 文件中。

| 字段名 | 类型 | 说明 | 示例（占位符） |
| --- | --- | --- | --- |
| `appId` | `string` | 飞书企业自建应用的 App ID | `cli_a1b2c3d4e5f6g7h8` |
| `App Secret` | `string` | 飞书自建应用的密钥。仅限在设置 UI 中填写，已保存时界面仅显示 `***`，留空或不修改该掩码会保留原密钥 | `********************` |
| `receive_id` | `string` | 接收方标识：`ou_` 开头按用户 `open_id` 发送私聊；`oc_` 开头按群聊 `chat_id` 发送（也可复用已有的会话 ID） | `ou_xxxxxxxxxxxxxxxx` 或 `oc_xxxxxxxxxxxxxxxx` |
| `enabled` | `boolean` | 通知总开关。关闭后跳过常规通知与长任务收尾摘要，但不影响手动点击「发送测试消息」 | `true` |
| `quietHours.start` | `string` | 免打扰开始时间（`HH:mm`） | `23:00` |
| `quietHours.end` | `string` | 免打扰结束时间（`HH:mm`）。支持跨午夜时段；当 `start == end` 时表示全天免打扰 | `08:00` |
| `quietHours.timeZone` | `string` | 免打扰计算的 IANA 时区名称 | `Asia/Shanghai` |

### 飞书后台权限核对

启用前请对照飞书开放平台官方后台核对自建应用配置：

- 应用已启用机器人能力，并已开通发送消息所需权限。
- 使用 `ou_`（`open_id`）时，目标用户需在应用可见范围内；使用 `oc_`（`chat_id`）时，需确保机器人已加入目标群聊或对应会话。
- 设置页存在未保存修改时，请先点击保存再执行「发送测试消息」。界面仅在飞书接口返回成功后才提示成功，失败时会直接展示飞书返回的错误码与错误说明。

## 安全与隐私边界

- **本地凭据保护**：宿主将配置写入当前 profile 的 `feishu-notify.json` 时，采用同目录临时文件加原子重命名写入，文件权限设为 `0600`。
- **密钥隔离**：`App Secret` 仅存储在宿主机本地，后端 API 不向前端返回明文；模型侧工具（`notify_user` 与 `feishu_notify`）无权读取或修改 `App Secret`。
- **禁止提交凭据**：`feishu-notify.json` 及运行备份包含真实凭据与接收方标识，切勿提交到版本控制仓库，也不要将真实 `appId`、密钥或 `receive_id` 粘贴到公开文档、问题报告或日志中。
- **外发内容说明**：通知会将用户授权的工作摘要或待处理提醒发送到飞书服务器及指定接收方。通知正文采取最小化原则，不附带应用凭据、本地 profile 路径或敏感会话原文。

## 常见问题（FAQ）

### 为什么点击「发送测试消息」在关闭总开关或免打扰时段内仍会收到飞书消息？

「发送测试消息」用于即时检验已保存的飞书凭据与 `receive_id` 是否连通，设计上会绕过 `enabled` 总开关和 `quietHours` 免打扰时段。如果界面修改了表单项，请先保存再点击测试。

### 为什么单次对话回合超过 3 分钟，模型却没有调用 `notify_user`？

3 分钟阈值针对的是用户请求的“整体任务”并在完成或收尾时触发，宿主不会在单回合满 3 分钟时强行截断或自动发信。若当前仅处于子任务、中间进度或内部报错重试阶段，模型按规则不会发送通知。

### 跨多轮对话的同一个长任务，会不会重复发送完成通知？

代码层面仅拦截同一回合（turn）内的并发与成功后再调用；跨回合的去重依靠会话投影中的成功回执记录与提示词约束模型自律完成，目前没有基于持久化跨回合任务 ID 的硬性自动幂等锁。

### 免打扰时段的 `start` 和 `end` 设置为相同时间代表什么？

当 `quietHours.start` 与 `quietHours.end` 相等（例如均为 `00:00`）时，系统判定为全天处于免打扰时段，常规自动提醒与 `notify_user` 均会返回 `skipped`。
