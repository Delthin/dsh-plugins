# Prompt composition host adapter

This directory is an explicit, reversible local host adaptation, not a public DSH API and not an npm lifecycle action. The plugin supports hosts at or above its declared minimum; this adapter only accepts the exact audited 0.2.2-rc.1 and 0.2.2-rc.3 file shapes. The Lead must review and explicitly apply it. It never restarts a process.

## UI/backend contract

`GET/PUT /api/tool-discovery/prompt-composition` returns `{config,sources,capabilities}`. Configuration is independently stored in `prompt-composition.json`: `{version:1,enabled:false,order:[],rules:{}}`. A rule is `{role:'inherit'|'system'|'developer'|'user',delivery:'inherit'|'always'|'pack',placement?:'inherit'|'fixed'|'state',enabled?:boolean}`. Optional `placement` preserves legacy configuration; placement inheritance is field-local. PUT validates capabilities and source identity before persisting; unsupported choices fail, rather than pretending to save.

Stable contribution IDs are `section:<encoded owner>:<encoded registration name>`, `context:<encoded owner>:<encoded registration name>`, and `instructions:<encoded real-file key>` (the source's absolute file identity; the display path is only its label). AGENTS grouping IDs are `instructions:global` and `instructions:project`; file rules override their group. Source metadata contains `id,label,owner,kind,defaultRole,roles,defaultPlacement,placements,deliveryModes,reason,children?,catalogOrigin?`. `catalogOrigin` distinguishes global registrations (`registered`) from identity-only observations across conversations (`observed`); catalog membership is not proof of inclusion in a particular request. Adapted hosts expose `capabilities.placements=["inherit","fixed","state"]`; unsupported hosts expose `["inherit"]`. Registration string literals, AGENTS, instructions and catalogs default to fixed; providers, snapshots and unclassified sources default to state, without evaluating providers or accessors. Registry ownership comes from the actual Cordis registration context, never a prompt-name prefix. Unattributed final-assembly contributions remain visible, orderable and configurable as system/user; they cannot follow a guessed plugin's pack. Trusted pre-step messages use native ContextFormed instructions/catalog/snapshot metadata and IDs `message:<encoded source.kind>:<form>:<encoded source.name>`, grouped by `message-source:<encoded source.kind>`. Ordinary user messages and generic notice/relay/recall data are excluded. The audited dsh-mnemon createPluginMessage envelope participates only when its form is `instructions`. Mnemon `recall` data and `memory-snapshot` messages retain their exact IDs, source metadata, content, role and order; Mnemon owns their lifecycle, including recognition of legacy runtime snapshots. Composition neither infers state from their text nor promotes them through owner rules.

The unwrap directory is a separate `tool-discovery:directory` section owned by `@delthin/dsh-tool-wrap`, always available when deferred packs exist. It cannot defer itself.

### Safe registration previews

Global registered section/context sources include `source.preview`:

- `{kind:'static',text:string}` contains the complete, unchanged registration literal, including empty strings and unresolved `{{variable}}` references. It is not the final rendered session prompt.
- `{kind:'dynamic',reason:'session-context-required',message:string}` means the registered `text` is a provider requiring session context. The message explains why no body is available; `text` is omitted.
- `{kind:'unavailable',reason:'static-text-unavailable',message:string}` means no safe own data-property string/provider was found (for example, an accessor or unsupported definition). `text` is omitted.

The audited SystemPrompt contract uses `text: string | ((context: AssembleContext) => string)` for both sections and contexts; contexts have no separate `render` field. Preview generation reads only global registration data properties. It never assembles a prompt, invokes providers/accessors/variables, interpolates text or serializes function source. The existing authenticated GET/status response passes these previews through independently of host-adapter availability. Clients can show `preview.text` for static sources and `preview.message` for dynamic/unavailable sources.

Scoped registrations and observed assembly/message/AGENTS bodies are excluded. Observed sources retain identity metadata only and do not acquire previews from session content; groups and unavailable stored IDs also have no registration preview. A scoped shadow or the most recent session cannot replace a global registration preview. Dynamic/session-only content would require a separately authorized caller-scoped preview API; it must not be cached into global status.

## Admission boundary

The host hook executes after complete-persona enforcement, runtime-context refresh and pre-step hooks, but before any contributed message is admitted to the session surface. It is not a request/stream rewrite. Ordinary conversation messages are never supplied as configurable instruction contributions. The unmodified path remains byte/order/role compatible when composition is disabled.

The host retains original instruction payloads and IDs inside durable hidden source-authority nodes on the surface, without first appending and replacing visible producer input; composed snapshots use ordinary system/user message events; developer is not currently supported. Fixed and state user projections reconcile independently. Automatic fixed-body changes append per-source overrides; natural removals append explicit revocations. Refreshed state appends a complete superseding snapshot after current input, preserving previous visible snapshots and the entire prior message prefix; unchanged state adds nothing. Explicit source exclusions and role/placement changes revoke the affected historical copies, while sorting may reproject only the necessary fixed suffix. A hidden, replayable control tracks current fixed ordering and state identity without entering model messages. Only a one-to-one replacement whose old and new nodes are explicitly empty composition bookkeeping and have no effective projected message preserves `contentGeneration`; positional replacement history and `replaceGeneration` still advance. Native message projections, visible replacements, generic empty messages and multi-node ranges still invalidate normally, preserving native request-series/tool-history resets for real history changes. Both server and browser surface folds use the same exception. Logged surface operations preserve ordinary conversation/tool history and permit reconstruction solely from the session log. Legacy projections without placement are treated as fixed until reclassified. Legacy Mnemon recall/snapshot authority nodes restore their original content and IDs in place, and their old fixed/state user projections are withdrawn. Before admission restores captured data, Mnemon's pre-step snapshot preparation must inspect the authority's original content and retire obsolete snapshots; otherwise restoring a captured legacy runtime snapshot can reintroduce stale state for that request. Former system promotions lose their source authority and use the existing system-source guard to normalize all old system copies. This one-time correction changes the prior cache prefix; replay and unchanged admissions add no duplicate migration events. AGENTS rendering attaches exact per-file blocks during budget rendering; admission does not split or infer boundaries from prose.

Pack delivery requires an identified plugin and a caller-visible deferred tool in that plugin. Guidance comes from the calling scope/toolSet’s accepted step, without re-evaluating dynamic providers or sharing bodies between conversations. A successful visible root-call result activates that pack for this session; subsequent admissions place its guidance in the configured real system/user role. The small activation event stores only plugin/root-call identity. Activation is reconstructed against visible successful results, so replay preserves it and rewinding/removing the result cancels it. Schema definitions remain tool results, not elevated instructions. When the model supports in-history system updates, a continuing composition whose previous system-source IDs retain their relative order keeps that native path, including source additions without authority loss. First activation, disabling, lost or moved system authorities, and unknown legacy authority metadata still normalize old system nodes so high-privilege copies cannot survive demotion. Changing roles/order or activating guidance can change the system text and its cache prefix; actual service cache-hit equivalence is not claimed. Required contexts are refreshed before composition, so delivery is not undone by host refresh. Tool admission, guard, approval, sandbox and native transport behavior remain owned by the existing host.

## Updating an adapted installation

Updating the npm plugin replaces the packaged adapter assets, not the host files previously patched by them. When a release changes the adapter, run the following from the updated plugin directory, using the original installation root and its existing backup/manifest directory:

```bash
node host-support/adapter.mjs --check --root <installation-root> --backup <existing-backup-directory>
node host-support/adapter.mjs --apply --root <installation-root> --backup <existing-backup-directory>
```

Review the check before applying. The existing manifest authenticates an upgrade from the previously installed helper and preserves original host backups. After application, the user restarts DSH and refreshes the browser. A DSH package upgrade may replace patched host files; check against the newly installed host before reapplying. The adapter selects its audited profile from the installed package version and rejects mixed versions or unknown hashes. Keep the same backup directory for updates within one host version. When changing host versions, omit `--backup` to use the version-specific default (the legacy `.tool-wrap-host-adapter-v1` for rc1 and `.tool-wrap-host-adapter-v1-0.2.2-rc.3` for rc3), or choose a fresh directory; never reuse another host version's originals. The rc3 profile uses `runtimeContext.project(sections)` and reads pending batch candidates during bookkeeping checks. AGENTS contributions preserve native compact/budget fallbacks and include the introduction only once.

The prefix-preservation rules and the repaired history rewrites are summarized in the [English README](<../README.en.md#automatic-updates-and-cache-prefixes>) and [Chinese README](<../README.md#自动更新与缓存前缀>).

## Review and application

The adapter script supports `--check`, `--apply` and `--restore`, with an explicit installation root. It verifies package versions, exact source hashes and all patch anchors before touching files. Backups and a manifest permit restoration only when the installed patched hash still matches. An explicit apply may upgrade an existing admission helper only when its hash, installation root and helper path match the recorded manifest; independent edits remain protected. It does not change package version ranges or touch runtime profiles. Never apply automatically during installation or synchronization.
